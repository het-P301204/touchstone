# The synthetic demo dataset

**Every vendor in the demo dataset is fictional.** Names such as "Northwind Systems" or "Halcyon Cloud" are invented,
every URL uses the reserved `.example` top-level domain, and every record id has the form `DEMO-YYYY-NNNN`, which no
real CVE record can have. Each vendor carries `synthetic: true`, and the web app, API and reports label it. The figures
illustrate the method and its edge cases; they say nothing about any real company.

## Why synthetic

Publishing measurements of real vendors carries a duty of accuracy that a demonstration cannot meet. The synthetic
cohort instead exercises every rule on purpose: a complete vendor, missing fields, placeholder CWEs, duplicate and
ambiguous records, an identity collision, VDPs that are strong, weak, prohibitive or missing, an expired security.txt,
stale and failed sources, a VDP that narrows between versions, a vendor below the minimum sample, and heavy third-party
enrichment.

The raw files go through the **same normalizers** as live data (`packages/collect/src/demo.ts loadDemoInputs`):
`parseSignerList` and `matchSignatories`, `normalizeCveRecord`, `normalizeCsafAdvisory`, `parseSecurityTxt`,
`htmlToText` and `assessVdp`. Nothing is pre-digested. Each file's sha256 is checked against the version manifest and
every snapshot id is recomputed on load; a mismatch stops the load.

## Layout

Generated by `scripts/demo/generate.ts` from the vendor specifications in `scripts/demo/vendors.ts`, with a seeded PRNG
(mulberry32, seed 20261006, keyed per vendor) so the output is byte-identical on every run.

```
fixtures/demo/
  registry/vendors.json                       Vendor[] (aliases with evidence; signatory status is set from the signer page)
  records/cve/<id>-<sha8>.json                CVE JSON 5.1 records, one file per distinct content
  records/csaf/<vendorId>/<trackingId>.json   CSAF 2.0 advisories
  <version>/manifest.json                     sources and the snapshot list (sourceId, url, fetchedAt, status, file, sha256)
  <version>/cisa/signers.html                 signer page with the same structure as the real CISA page
  <version>/vdp/<vendorId>/security.txt       RFC 9116 file
  <version>/vdp/<vendorId>/policy.html        policy page
  expected/<runId>.manifest.json              the expected manifest of each published run
  SCENARIOS.md                                vendor -> scenario -> expected outcome (generated)
```

The generator reports 1073 files (2.98 MB) under `fixtures/demo`.

(`foxglove-identity`) is placed against peers without shaping their medians. A run id changes whenever the inputs or
the methodology fingerprint change.

## Regenerating

All three commands run offline.

```
npm run demo:generate   # node scripts/demo/generate.ts: rewrite fixtures/demo from scripts/demo/vendors.ts
npm run demo:build      # node scripts/build-demo.ts: run the pipeline over every version, write apps/web/public/data
                        #   and fixtures/demo/expected
npm run demo:check      # regenerate both in memory; exit 1 if any committed file differs
```

`demo:build` processes the versions in order and feeds each run's figures into the next run's history, so historical
medians and trend lines come from the same pipeline the API uses. It also writes the synthetic seed disputes and
notebook entries. CI runs `demo:check` on every push, so the committed fixtures, the published bundle and the expected
manifests can never drift from the generator and the engine.

Do not edit files under `fixtures/demo` by hand: change `scripts/demo/vendors.ts` (or the generator) and regenerate.
A methodology or engine change that alters any figure shows up as a difference in `fixtures/demo/expected/*.manifest.json`
(see [CONTRIBUTING.md](../CONTRIBUTING.md#changing-the-methodology)).
